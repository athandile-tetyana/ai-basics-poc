PreOrder Kasi — Technical Spec

The blueprint for how we'll build what the PRD describes.

How it works: One Next.js app with a frontend (what people see) and backend API routes (logic + database). SQLite file on disk for persistence. Groq free API for AI order parsing. Plain CSS for styling. One command to start, two tabs to demo.

Stack

  • Next.js 15 (App Router) — React framework, frontend + API routes in one project. Docs
  • better-sqlite3 — SQLite library, raw SQL queries, no ORM. Docs
  • Groq API — Free-tier AI for order parsing, structured JSON output. Docs
  • Plain CSS modules — Scoped CSS per component, no build tools.

Architecture Diagram

The Core Journey Through the System

1
User opens the app
Next.js serves the home page with two buttons.
2
Customer taps "I'm a customer"
Next.js serves the order form page with AI text box and manual fields.
3
Customer types order and clicks Parse
Browser sends text to /api/parse → API route calls Groq → Groq returns JSON → form fields filled.
4
Customer submits order
Browser sends order to /api/orders → API route checks seller match → saves to SQLite → returns order with reference number.
5
Customer sees confirmation
Browser shows order details, status (Pending), and reference number.
6
Seller opens app in another tab
Taps "I'm a seller" → /api/seller/orders reads all orders from SQLite → dashboard rendered.
7
Seller confirms an order
Browser sends confirmation to /api/seller/orders/[id]/confirm → API route updates SQLite status to "confirmed".
8
Seller views prep list
/api/seller/prep-list reads confirmed orders from SQLite → groups by pickup time → browser renders grouped list.
9
Seller marks collected
Browser sends update to /api/seller/orders/[id]/collect → API route updates SQLite status to "collected".
10
Customer refreshes
Browser calls /api/orders/[id] → reads latest status from SQLite → customer sees update.

Components

Home Page ▼

Two large buttons: "I'm a customer" and "I'm a seller". "Look up my order" link. Entry point for all flows.

PRD ref: prd.md > Screens and Layout > 1. Home Screen

Customer Order Form ▼

AI text box with "Parse" button. Manual form fields: Name, Item, Quantity, Pickup Date, Pickup Time, Location. Submit button.

Calls /api/parse for AI parsing, /api/orders for submission.

PRD ref: prd.md > Features and Behavior > Customer: Place a Pre-Order

Customer Order Confirmation ▼

Order details, customer name, reference number, current status. "Check status" button.

Calls /api/orders/[id] to refresh status.

PRD ref: prd.md > Features and Behavior > Customer: Check Order Status

Order Lookup ▼

Single input for reference number. Shows order details and current status.

Calls /api/orders/[id] to fetch order.

PRD ref: prd.md > Features and Behavior > Customer: Look Up Order

Seller Setup Form ▼

Name, items (comma-separated), availability window (start/end time).

Calls /api/seller/setup to create seller profile.

PRD ref: prd.md > Features and Behavior > Seller: One-Time Setup

Seller Dashboard ▼

Lists all incoming orders. Confirm/Decline buttons for pending orders. Link to prep list.

Calls /api/seller/orders for list, /api/seller/orders/[id]/confirm and /api/seller/orders/[id]/decline for actions.

PRD ref: prd.md > Features and Behavior > Seller: Manage Incoming Orders

Seller Prep List ▼

Confirmed orders grouped by pickup time slot. Mark as "collected" or "not collected".

Calls /api/seller/prep-list for grouped data, /api/seller/orders/[id]/collect for status updates.

PRD ref: prd.md > Features and Behavior > Seller: View Prep List and Seller: Mark Orders as Collected

Database Module ▼

Singleton connection to SQLite file (data/preorder.db). Creates tables on first run. Exports query functions used by API routes.

PRD ref: prd.md > Features and Behavior > Data Persistence

AI Parse Module ▼

Sends order text to Groq API with a JSON schema. Returns structured data: { item, quantity, date, time }. Handles API errors gracefully.

PRD ref: prd.md > Features and Behavior > Customer: AI-Assisted Order Entry

Data Model

sellers table

  • id — Primary key, auto-increment
  • name — Seller name
  • items — Comma-separated list of items
  • available_start — Availability window start (e.g. "16:00")
  • available_end — Availability window end (e.g. "20:00")
  • created_at — Timestamp

orders table

  • id — Primary key, auto-increment (used as reference number)
  • customer_name — Customer's name
  • item — Food item ordered
  • quantity — Number of items
  • pickup_date — Pickup date (ISO format)
  • pickup_time — Pickup time (HH:MM format)
  • location — Pickup location (text)
  • status — pending, confirmed, declined, collected, not_collected
  • seller_id — Foreign key to sellers table
  • created_at — Timestamp

External Services

Groq API

  • Endpoint: POST https://api.groq.com/openai/v1/chat/completions
  • Auth: Bearer token (GROQ_API_KEY environment variable)
  • Model: openai/gpt-oss-120b (free tier, supports structured outputs)
  • Rate limits: 30 requests/min, 1,000 requests/day
  • Cost: Free
  • Docs: console.groq.com/docs

better-sqlite3

  • No external service — local file database
  • npm package: better-sqlite3
  • Docs: github.com/WiseLibs/better-sqlite3

Important Failure Modes

  • Groq API is slow or fails → Parse route returns error. Customer sees "Couldn't parse that — please fill in the form manually." Form is always available as fallback.
  • No seller matches the order → Order route returns "No seller available for that item or time." Customer can try different item or time.
  • Seller has no orders yet → Dashboard shows "No orders yet". Prep list shows "No confirmed orders yet."
  • Invalid reference number → Lookup returns "Order not found."
  • Database file doesn't exist → db module creates it and tables on first run. No manual setup needed.

What Was Simplified and Why

  • Single seller for hackathon instead of multi-seller matching — keeps demo simple, data model clean.
  • No real-time updates instead of websockets — refresh/check status is enough for the demo.
  • No authentication instead of login system — name fields only, no auth complexity.
  • No prices/payments instead of payment system — cash on collection, outside core loop.
  • Plain CSS instead of Tailwind — no build step, no utility classes.
  • better-sqlite3 instead of ORM — raw SQL queries, visible and explainable.

Decisions and Open Issues

  • Next.js with App Router — learner is comfortable with Next.js, handles frontend + API routes in one project.
  • better-sqlite3 — simplicity and transparency. Raw SQL means writing queries by hand, but that's a feature for learning.
  • Groq API with gpt-oss-120b — free tier, speed, structured output support. Rate limits are plenty for a demo.
  • Plain CSS modules — minimal stack. No utility classes or design tokens.
  • Single seller for hackathon — seller setup form exists but demo uses one seller.
  • No real-time updates — refresh/check status is sufficient for the demo.

Open questions: None blocking the build.
